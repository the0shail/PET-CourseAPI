# ЧАСТЬ I. ПОЛНЫЙ РЕЕСТР ЭНДПОИНТОВ

## 0. Общие соглашения

### 0.1 Базовый путь и версия
Все эндпоинты — под `/api/v1`. Версия в пути, а не в заголовке: проще для Swagger, проще для curl, видно в логах nginx.

### 0.2 Аутентификация
`Authorization: Bearer <access_token>`. Отсутствие или невалидность токена там, где он обязателен → `401`. Токен есть, но прав на конкретный ресурс нет → `403`.

### 0.3 Уровни доступа

| Обозначение | Смысл |
|---|---|
| `public` | без токена |
| `auth` | любой аутентифицированный |
| `STUDENT` / `INSTRUCTOR` / `ADMIN` | проверка роли (`@PreAuthorize("hasRole(...)")`) |
| `owner` | проверка владения ресурсом: автор курса, владелец записи, автор отзыва |
| `owner+ADMIN` | владелец **или** админ |

**Ключевое различие.** Роль отвечает на вопрос «что вообще может делать этот тип пользователя», владение — «его ли это конкретная строка в таблице». `INSTRUCTOR` может редактировать курсы, но только свои. Обе проверки нужны, и вторая не выводится из первой.

### 0.4 Пагинация

Все списочные эндпоинты принимают:

| Параметр | По умолчанию | Ограничение |
|---|---|---|
| `page` | `0` | ≥ 0 |
| `size` | `20` | 1..100, больше → `400` |
| `sort` | зависит от ресурса | только из белого списка полей |

`size` жёстко ограничен сверху: без потолка `?size=1000000` — это DoS одним GET-запросом.

Схемы всех тел ответов — в §15; в таблице §1 они указаны по имени.

**Формат ответа списка.** Не `Page` Spring Data напрямую — его JSON не является стабильным контрактом и Boot предупреждает об этом в логах. Свой record:

```json
{
  "content": [ ... ],
  "page": { "number": 0, "size": 20, "totalElements": 137, "totalPages": 7 }
}
```

Альтернатива — `PagedModel` из Spring Data, оборачивающий `Page`. Выбор своего record'а — ради полного контроля над контрактом.

### 0.5 Сортировка
Формат `sort=field,direction`, например `sort=price,asc`. Поле проверяется по белому списку — иначе через `sort` можно упорядочить по любому полю сущности, включая `password_hash`, что даёт бинарный поиск по хешам. Поле вне списка → `400 INVALID_SORT_FIELD`.

### 0.6 Частичное обновление
`PATCH` с семантикой «переданные поля обновляются, остальные не трогаются». Отличить «не передано» от «передано `null`» в record'ах нельзя, поэтому в PATCH-DTO опциональные поля — `JsonNullable<T>` (`org.openapitools:jackson-databind-nullable`) либо обычные nullable-поля с соглашением «null = не менять». Для этого проекта достаточно второго варианта; ограничение фиксируется в OpenAPI-описании.

### 0.7 Ответы на изменяющие операции

| Операция | Код | Тело |
|---|---|---|
| Создание | `201 Created` + `Location` | созданный ресурс |
| Обновление | `200 OK` | обновлённый ресурс |
| Смена состояния (publish/archive/cancel) | `200 OK` | ресурс с новым статусом |
| Удаление | `204 No Content` | пусто |
| Асинхронно принято | `202 Accepted` | ссылка на статус |

### 0.8 Формат ошибок

Единый (как в §5 основного ТЗ), плюс поле `details` для ошибок валидации:

```json
{
  "timestamp": "2026-08-21T10:15:30Z",
  "status": 400,
  "error": "VALIDATION_ERROR",
  "message": "Запрос не прошёл валидацию",
  "path": "/api/v1/courses",
  "details": [
    { "field": "title", "message": "не должно быть пустым" },
    { "field": "price", "message": "должно быть больше или равно 0" }
  ]
}
```

`error` — машиночитаемый код из фиксированного каталога (§12), `message` — человекочитаемый текст. Клиент ветвится по `error`, показывает `message`.

### 0.9 Сокрытие существования ресурса

Для `DRAFT`-курсов и уроков закрытых курсов возвращается `404`, а не `403`. `403` подтверждает, что ресурс с таким id существует — это утечка. Перебором `/courses/1..10000` можно узнать, сколько черновиков у конкурента и в какие моменты они появляются.

Исключение: если пользователь **знает** о ресурсе (пытается изменить свой курс в неправильном статусе) — честный `403`/`409`.

## 2. Аутентификация

### 2.1 `POST /auth/register`

Доступ: `public` · Успех: `201 Created`

```json
{
  "email": "ivan@example.com",
  "password": "S3cret!Pass",
  "firstName": "Иван",
  "lastName": "Петров",
  "role": "STUDENT"
}
```

| Поле | Правила |
|---|---|
| `email` | `@Email`, `@NotBlank`, ≤ 255, приводится к нижнему регистру |
| `password` | `@Size(min = 8, max = 72)`, минимум одна буква и одна цифра |
| `firstName`, `lastName` | `@NotBlank`, ≤ 100 |
| `role` | только `STUDENT` или `INSTRUCTOR`; отсутствует → `STUDENT` |

**Решения.**

- Верхняя граница пароля в 72 символа — не прихоть: bcrypt молча обрезает вход после 72 байт. Без явной валидации пароли длиннее 72 символов совпадают по первым 72 байтам, о чём никто не узнает.
- `ADMIN` через регистрацию не выдаётся никогда. Первый админ появляется миграцией-сидом, дальше — через `PATCH /admin/users/{id}/role`.
- Email нормализуется к нижнему регистру **до** проверки уникальности, иначе `Ivan@` и `ivan@` — два аккаунта, а `UNIQUE` в базе регистрозависим. Альтернатива — `CITEXT` в PostgreSQL или функциональный уникальный индекс по `lower(email)`.
- Пользователь и профиль создаются в одной транзакции (`@Transactional` в сервисе).

Ответ `201`:

```json
{
  "id": 42,
  "email": "ivan@example.com",
  "role": "STUDENT",
  "profile": { "firstName": "Иван", "lastName": "Петров", "bio": null, "avatarUrl": null },
  "createdAt": "2026-08-21T10:15:30Z"
}
```

Токены при регистрации не возвращаются — клиент вызывает `/auth/login`. Это разделяет два разных действия и упрощает добавление подтверждения email позже.

Ошибки: `400 VALIDATION_ERROR`, `409 EMAIL_ALREADY_EXISTS`.

### 2.2 `POST /auth/login`

Доступ: `public` · Успех: `200`

```json
{ "email": "ivan@example.com", "password": "S3cret!Pass" }
```

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
  "refreshToken": "eyJhbGciOiJIUzI1NiJ9...",
  "tokenType": "Bearer",
  "expiresIn": 900
}
```

**Решения.**

- Access — 15 минут, refresh — 30 дней. Access не отзывается (в этом смысл stateless), поэтому его время жизни короткое: окно ущерба от утёкшего токена ограничено.
- Refresh хранится в БД как хеш (таблица `refresh_tokens`, §21.1) — иначе `POST /auth/logout` невозможен физически, а «выйти со всех устройств» тем более.
- Ответ на неверный пароль и на несуществующий email — **одинаковый** `401 INVALID_CREDENTIALS`. Разные ответы превращают форму логина в перечислитель зарегистрированных email'ов.
- Проверка пароля выполняется даже для несуществующего пользователя (сравнение с фиктивным хешем) — иначе разницу в 200 мс на bcrypt видно секундомером и энумерация возвращается через тайминг.

Ошибки: `400 VALIDATION_ERROR`, `401 INVALID_CREDENTIALS`, `403 USER_BLOCKED`.

### 2.3 `POST /auth/refresh`

Доступ: `public` · Успех: `200` (тот же формат, что у login)

```json
{ "refreshToken": "eyJ..." }
```

**Ротация.** Старый refresh помечается отозванным, выдаётся новый. Повторное использование уже отозванного токена — признак кражи: отзываются **все** токены пользователя, ответ `401 REFRESH_TOKEN_REUSED`.

Ошибки: `401 INVALID_REFRESH_TOKEN`, `401 REFRESH_TOKEN_EXPIRED`, `401 REFRESH_TOKEN_REUSED`.

### 2.4 `POST /auth/logout`

Доступ: `auth` · Успех: `204`

```json
{ "refreshToken": "eyJ...", "allDevices": false }
```

Отзывает переданный refresh (или все токены пользователя при `allDevices: true`). Access-токен продолжает работать до истечения — это цена stateless-архитектуры и её надо понимать, а не маскировать. Если нужен мгновенный отзыв — нужен blacklist в Redis, то есть отказ от чистого stateless.

### 2.5 `POST /auth/password`

Доступ: `auth` · Успех: `204`

```json
{ "currentPassword": "old", "newPassword": "new" }
```

Смена пароля отзывает все refresh-токены, кроме текущего. Ошибки: `400 VALIDATION_ERROR`, `401 INVALID_CREDENTIALS`.

## 3. Пользователи

### 3.1 `GET /users/me`
Доступ: `auth` · `200`. Полный профиль + email + роль + `createdAt`. Ошибок, кроме `401`, нет: id берётся из токена.

### 3.2 `PATCH /users/me`
Доступ: `auth` · `200`

```json
{ "firstName": "Иван", "lastName": "Петров", "bio": "...", "avatarUrl": "https://..." }
```

Меняется только профиль. Email и роль здесь **не меняются**: смена email требует подтверждения, смена роли — прерогатива админа. Попытка передать `role` или `email` игнорируется молча (поля просто отсутствуют в DTO) — это надёжнее, чем проверять их в коде.

Ограничения: `bio` ≤ 2000, `avatarUrl` — `@URL`, ≤ 512.

### 3.3 `GET /users/{id}`
Доступ: `public` · `200`

Публичная карточка: `id`, `firstName`, `lastName`, `bio`, `avatarUrl`, `role`, `createdAt`, `publishedCoursesCount`. **Без email** — иначе API становится выгрузкой адресной базы по `/users/1..N`.

Ошибки: `404 USER_NOT_FOUND`.

### 3.4 `GET /users/{id}/courses`
Доступ: `public` · `200` · Пагинация

Только `PUBLISHED` курсы автора. `sort`: `createdAt`, `rating`, `popularity`. Ошибки: `404 USER_NOT_FOUND`.

### 3.5 `DELETE /users/me`
Доступ: `auth` · `204`

Удаление аккаунта. Профиль, записи и отзывы уходят каскадом (§3.2 основного ТЗ), но при наличии курсов — `409 USER_HAS_COURSES`: `courses.author_id` объявлен `ON DELETE RESTRICT` намеренно.

**Решение.** Ответ `409` здесь — не отговорка, а прямое следствие схемы. Автор с курсами должен сначала архивировать или передать курсы. В реальном продукте вместо удаления делается анонимизация (email → `deleted-42@…`, профиль очищается, строка остаётся) — контент выживает, персональные данные исчезают. Для портфолио достаточно `409` с объяснением в README.

## 4. Категории

### 4.1 `GET /categories`
Доступ: `public` · `200`

Плоский список без пагинации, отсортированный по `name`.

**Решение и его цена.** §4.5 основного ТЗ требует пагинацию везде. Здесь сделано исключение: категории — ограниченный справочник, который редактирует только админ, десятки строк. Пагинация справочника создаёт больше проблем клиенту (собирать выпадающий список из страниц), чем решает. Чтобы исключение не превратилось в дыру, в репозитории стоит жёсткий потолок: если категорий станет больше 500, эндпоинт начнёт возвращать `500` с явной ошибкой, а не тихо тянуть всё в память. Исключение с сигнализацией лучше, чем исключение без неё.

### 4.5 `DELETE /categories/{id}`
`ADMIN` · `204`

Если категория привязана хотя бы к одному курсу → `409 CATEGORY_IN_USE` с количеством курсов в `message`.

**Решение.** Каскадно отвязать категорию от курсов было бы технически проще — `course_categories` со `ON DELETE CASCADE` сделает это сам. Но тогда одно неосторожное нажатие админа беззвучно раскатегоризирует сотни курсов, и восстановить связи будет нечем. Явный отказ с подсказкой «сначала перепривяжите N курсов» дороже в реализации и правильнее по последствиям.

## 5. Курсы

### 5.1 Жизненный цикл

```
                 publish
      ┌────────┐ ────────► ┌───────────┐
      │ DRAFT  │           │ PUBLISHED │
      └───┬────┘           └─────┬─────┘
          │  archive             │  archive
          │                      │
          ▼                      ▼
      ┌──────────────────────────────┐
      │          ARCHIVED            │
      └──────────────┬───────────────┘
                     │  restore (только если нет активных записей)
                     ▼
                 PUBLISHED
```

| Переход | Разрешён | Условия |
|---|---|---|
| `DRAFT → PUBLISHED` | да | предусловия публикации (§5.5) |
| `DRAFT → ARCHIVED` | да | — |
| `PUBLISHED → ARCHIVED` | да | — |
| `ARCHIVED → PUBLISHED` | да | повторная проверка предусловий |
| `PUBLISHED → DRAFT` | **нет** | `409 INVALID_STATUS_TRANSITION` |

**Решение.** Обратный переход `PUBLISHED → DRAFT` запрещён сознательно. На опубликованный курс уже записались студенты; снятие в черновик мгновенно отберёт у них доступ к оплаченному контенту, при этом строки `enrollments` останутся живыми и система окажется в состоянии «активная запись на несуществующий для студента курс». Инвариант «у активной записи всегда есть доступный курс» дешевле поддержать запретом одного перехода, чем костылями во всех запросах. Нужно временно скрыть курс — `ARCHIVED`: он исчезает из каталога, но остаётся доступен тем, кто уже записан.

Что можно делать в каждом статусе:

| Действие | DRAFT | PUBLISHED | ARCHIVED |
|---|---|---|---|
| Виден в каталоге | нет | да | нет |
| Виден автору/админу | да | да | да |
| Правка полей курса | да | да | нет |
| Правка модулей/уроков | да | да | нет |
| Новые записи | нет | да | нет |
| Доступ уже записанных | — | да | да |
| Новые отзывы | нет | да | да |

### 5.2 `GET /courses` — каталог

Доступ: `public` · `200` · Пагинация

| Параметр | Тип | Описание |
|---|---|---|
| `q` | string | поиск по названию и описанию, ≥ 2 символов |
| `categoryId` | long, повторяемый | `?categoryId=3&categoryId=7` — OR внутри |
| `priceMin` / `priceMax` | decimal ≥ 0 | диапазон включительно |
| `free` | boolean | `true` → только `price = 0`; конфликтует с `priceMin > 0` → `400` |
| `minRating` | decimal 1..5 | минимальный средний рейтинг |
| `authorId` | long | курсы конкретного автора |
| `page`, `size`, `sort` | | §0.4 |

Белый список `sort`: `createdAt` (по умолчанию, `desc`), `price`, `rating`, `popularity`, `title`.

Ответ — `PageResponse<CourseListItem>`:

```json
{
  "id": 42,
  "title": "Spring Boot с нуля",
  "shortDescription": "Первые 200 символов описания…",
  "price": 4990.00,
  "author": { "id": 7, "firstName": "Иван", "lastName": "Петров", "avatarUrl": null },
  "categories": [ { "id": 3, "name": "Backend-разработка" } ],
  "ratingAvg": 4.7,
  "ratingCount": 128,
  "studentsCount": 1543,
  "createdAt": "2026-05-01T09:00:00Z"
}
```

**Решения.**

- Фильтры собираются через `Specification` и комбинируются между собой (§4.5 основного ТЗ). Каждый фильтр — статический метод, возвращающий `Specification<Course>` или `null`; общий фильтр — `Specification.allOf(...)` с отсевом null'ов. Один метод репозитория вместо комбинаторного взрыва.
- Фильтр по статусу **не является параметром**. `status = PUBLISHED` добавляется сервисом всегда и не управляется извне: иначе `?status=DRAFT` открывает чужие черновики.
- `q` — `ILIKE '%…%'` на старте. Это гарантированный seq scan: индекс по префиксу тут не работает. Честный путь дальше — GIN-индекс с `pg_trgm` либо полнотекстовый поиск PostgreSQL (`to_tsvector`), это отмечено в §11 основного ТЗ. Важно не притворяться, что `ILIKE` масштабируется.
- **`sort=rating` и `sort=popularity` — отдельная проблема.** Это вычисляемые величины, `Sort` по полю сущности для них не работает. Три варианта: (а) join + `GROUP BY` + `ORDER BY AVG(...)` — ломает пагинацию и не дружит с `Specification`; (б) коррелированный подзапрос в `ORDER BY` — считает агрегат для каждой строки; (в) денормализованные колонки `rating_avg`, `rating_count`, `enrollment_count` в `courses` с индексами. Выбран вариант (в), и поддерживает их консьюмер RabbitMQ (§19.3) — так асинхронная обработка решает конкретную задачу каталога, а не добавлена ради галочки.
- Список отдаётся **DTO-проекцией**, а не мапингом полных сущностей: карточке каталога не нужны ни `description` целиком, ни модули, ни содержимое уроков.

Ошибки: `400 INVALID_SORT_FIELD`, `400 INVALID_FILTER_COMBINATION`.

### 5.3 `GET /courses/{id}` — карточка курса

Доступ: `public` (с оговоркой §0.9) · `200`

```json
{
  "id": 42,
  "title": "Spring Boot с нуля",
  "description": "Полное описание…",
  "price": 4990.00,
  "status": "PUBLISHED",
  "author": { "id": 7, "firstName": "Иван", "lastName": "Петров", "bio": "…", "avatarUrl": null },
  "categories": [ { "id": 3, "name": "Backend-разработка" } ],
  "ratingAvg": 4.7,
  "ratingCount": 128,
  "studentsCount": 1543,
  "modules": [
    {
      "id": 100, "title": "Введение", "orderIndex": 1,
      "lessons": [ { "id": 1000, "title": "Что такое Spring", "orderIndex": 1, "locked": false } ]
    }
  ],
  "viewerEnrollment": { "id": 555, "status": "ACTIVE", "progressPercent": 35 },
  "createdAt": "2026-05-01T09:00:00Z",
  "updatedAt": "2026-08-01T12:00:00Z"

```

**Решения.**

- Структура курса отдаётся **без содержимого уроков** — только заголовки и `locked`. Иначе платный курс полностью выдаётся анонимному запросу.
- `locked` вычисляется от зрителя: `false` для автора, админа и записанного студента; `true` для остальных.
- `viewerEnrollment` — `null` для анонима и незаписанного. Это избавляет клиента от второго запроса «а я записан?».
- Загрузка — один запрос с `@EntityGraph` на `modules → lessons` вместо N+1 по модулям. Поскольку `open-in-view: false`, всё нужное грузится в сервисе явно.

Ошибки: `404 COURSE_NOT_FOUND` (в том числе для чужого черновика).

### 5.4 `POST /courses`

Доступ: `INSTRUCTOR`, `ADMIN` · `201`

```json
{
  "title": "Spring Boot с нуля",
  "description": "Полное описание курса",
  "price": 4990.00,
  "categoryIds": [3, 7]
}
```

| Поле | Правила |
|---|---|
| `title` | `@NotBlank`, 5..255 |
| `description` | `@NotBlank`, 20..10000 |
| `price` | `@NotNull`, `@DecimalMin("0.00")`, `@Digits(integer = 8, fraction = 2)` |
| `categoryIds` | ≤ 10 элементов, каждый существует |

Курс создаётся в статусе `DRAFT`. `author_id` берётся **из токена**; поле `authorId` в DTO отсутствует физически — так подделать авторство нельзя даже при ошибке в проверке.

`@Digits(integer = 8, fraction = 2)` согласован с `NUMERIC(10,2)`: без него слишком длинное число уйдёт в базу и вернётся `500` вместо `400`.

Ошибки: `400 VALIDATION_ERROR`, `404 CATEGORY_NOT_FOUND`.

### 5.5 `POST /courses/{id}/publish`

Доступ: `owner+ADMIN` · `200`

Предусловия проверяются **все сразу**, ответ перечисляет каждое нарушенное:

```json
{
  "timestamp": "2026-08-21T10:15:30Z",
  "status": 409,
  "error": "COURSE_NOT_READY_FOR_PUBLICATION",
  "message": "Курс не готов к публикации",
  "path": "/api/v1/courses/42/publish",
  "details": [
    { "field": "modules", "message": "нужен хотя бы один модуль" },
    { "field": "lessons", "message": "модуль «Введение» не содержит уроков" }
  ]
}
```

Проверяется: непустые `title` и `description`, ≥ 1 модуля, каждый модуль содержит ≥ 1 урока, у каждого урока непустой `content`, назначена ≥ 1 категория.

**Решение.** Проверять предусловия по одному и падать на первом — значит заставить автора публиковать курс пять раз подряд, каждый раз узнавая об одной новой проблеме. Список всех нарушений сразу — это разница между API, с которым работают, и API, с которым борются.

Побочный эффект: публикуется событие `course.published` (§18).

Ошибки: `403 NOT_COURSE_OWNER`, `404`, `409 COURSE_NOT_READY_FOR_PUBLICATION`, `409 INVALID_STATUS_TRANSITION`.

### 5.6 `POST /courses/{id}/archive` · `POST /courses/{id}/restore`

`owner+ADMIN` · `200`. `archive` — из `DRAFT` или `PUBLISHED`. `restore` — из `ARCHIVED` в `PUBLISHED` с повторной проверкой предусловий §5.5.

Событие `course.archived` рассылает уведомления записанным студентам.

### 5.7 `PATCH /courses/{id}`

`owner+ADMIN` · `200`. Меняются `title`, `description`, `price`, `categoryIds`. Статус здесь **не меняется** — для этого есть отдельные операции с предусловиями. Смена статуса через общий PATCH обошла бы всю проверку готовности к публикации.

`ARCHIVED` курс не редактируется → `409 COURSE_ARCHIVED`.

**Отдельно про цену.** Изменение `price` не затрагивает уже записанных — они записались по старой цене. В системе без платежей это соглашение, в системе с платежами понадобилась бы фиксация цены в `enrollments.price_paid`. Ограничение зафиксировано явно, чтобы не выглядело недосмотром.

### 5.8 `DELETE /courses/{id}`

`owner+ADMIN` · `204`

Разрешено, только если на курсе **никогда никто не записывался** (ноль строк в `enrollments`, включая `CANCELLED`). Иначе `409 COURSE_HAS_ENROLLMENTS` → архивировать.

Проверка в сервисе дублируется ограничением `ON DELETE RESTRICT` на `enrollments.course_id`: код проверяет, чтобы вернуть внятный `409`, база — чтобы гонка «проверили → успели записаться → удалили» не оставила висящих ссылок.

### 5.9 `GET /courses/my`

`INSTRUCTOR`, `ADMIN` · `200` · Пагинация

Все свои курсы, включая черновики и архив. Фильтр `?status=DRAFT`. Здесь `status` — легитимный параметр: показываются только собственные курсы.

### 5.10 `GET /courses/{id}/students`

`owner+ADMIN` · `200` · Пагинация

Записанные студенты: `enrollmentId`, публичный профиль, `status`, `progressPercent`, `enrolledAt`, `completedAt`. Фильтры `?status=ACTIVE`, `?minProgress=50`. Email студентов автору не показывается.

### 5.11 `PUT /courses/{id}/categories`

`owner+ADMIN` · `200`

```json
{ "categoryIds": [3, 7, 12] }
```

**Решение: `PUT` вместо пары `POST`/`DELETE` на подресурс.** Для `@ManyToMany` без собственных данных естественна операция «сделать набор таким» — она идемпотентна, не зависит от текущего состояния и не требует от клиента вычислять диффы. Пара `POST /courses/{id}/categories/{categoryId}` + `DELETE` дала бы более «RESTful» URL-ы ценой N запросов на переназначение и гонок между ними. Полная замена набора выигрывает.

Ошибки: `400` (> 10 категорий), `404 CATEGORY_NOT_FOUND`, `409 COURSE_ARCHIVED`.

## 6. Модули

### 6.1 `POST /courses/{courseId}/modules`
`owner+ADMIN` · `201`

```json
{ "title": "Введение в Spring", "orderIndex": 1 }
```

`title` — `@NotBlank`, 3..255. `orderIndex` — `@Min(1)`; если не передан, назначается `max + 1`.

Ошибки: `409 DUPLICATE_ORDER_INDEX` (нарушение `UNIQUE(course_id, order_index)`), `409 COURSE_ARCHIVED`.

### 6.2 `GET /courses/{courseId}/modules` · `GET /modules/{id}`
Автор, админ или записанный студент. Для остальных — `404`. Модуль отдаётся со списком уроков (заголовки + `locked`).

### 6.3 `PATCH /modules/{id}`
`owner+ADMIN` · `200`. Меняется `title`. `orderIndex` **здесь не меняется** — см. §6.5.

### 6.4 `DELETE /modules/{id}`
`owner+ADMIN` · `204`

Уроки уходят каскадом (`ON DELETE CASCADE` + `cascade = ALL, orphanRemoval = true` на стороне JPA).

Если курс `PUBLISHED` и это последний модуль → `409 PUBLISHED_COURSE_REQUIRES_CONTENT`.

**Решение.** Предусловия публикации (§5.5) требуют минимум один модуль с уроком. Проверить их один раз при публикации и больше никогда — значит позволить опубликованному курсу стать пустым через час: инвариант, который держится только в момент проверки, не инвариант. Правило действует на весь жизненный цикл `PUBLISHED`.

### 6.5 `PUT /courses/{courseId}/modules/order`
`owner+ADMIN` · `200`

```json
{ "order": [ { "moduleId": 102, "orderIndex": 1 }, { "moduleId": 100, "orderIndex": 2 } ] }
```

**Почему переупорядочивание — отдельный эндпоинт.** `UNIQUE(course_id, order_index)` делает поштучное изменение порядка невозможным: чтобы поменять местами модули 1 и 2, надо присвоить первому `2`, а он уже занят — `UPDATE` падает на середине. Клиент, дёргающий `PATCH /modules/{id}` дважды, получит `409` и разъехавшийся порядок.

Три способа решить, все рабочие:

1. **Батч в одной транзакции с временным сдвигом** — сначала всем участвующим модулям присваиваются отрицательные индексы, потом целевые. Работает на любой СУБД, никаких особых настроек.
2. **`DEFERRABLE INITIALLY DEFERRED`** на уникальном ограничении — проверка откладывается до `COMMIT`, промежуточные коллизии допустимы. Требует объявить это в миграции заранее; в PostgreSQL работает только для `UNIQUE`/`PK`, не для частичных индексов.
3. **Дробные индексы** (`NUMERIC` вместо `INT`): вставка между 1 и 2 даёт 1.5, переупорядочивание не трогает соседей. Ценой периодической ренумерации, когда знаменатели вырастают.

Выбран вариант 1 — явный, самодокументируемый, не требует чтения миграции для понимания кода. Запрос обязан содержать **все** модули курса: частичный список — половина проблем с уникальностью обратно.

Ошибки: `400 INCOMPLETE_ORDER` (переданы не все модули), `400 DUPLICATE_ORDER_INDEX` (дубли внутри запроса), `404`.

## 7. Уроки

### 7.1 `POST /modules/{moduleId}/lessons`
`owner+ADMIN` · `201`

```json
{ "title": "Что такое Spring", "content": "Markdown-текст урока", "orderIndex": 1 }
```

`title` — `@NotBlank`, 3..255; `content` — `@NotBlank`, ≤ 100 000; `orderIndex` — `@Min(1)`, по умолчанию `max + 1`.

### 7.2 `GET /lessons/{id}`
Доступ: автор, админ или студент с записью `ACTIVE`/`COMPLETED` на курс этого урока.

**Порядок проверки важен.** Сначала «существует ли урок», потом «имеет ли зритель доступ». Нет доступа → `404`, а не `403` (§0.9). Проверка требует пути `lesson → module → course → enrollment`: один запрос с явными join'ами, а не четыре обращения к репозиторию.

Ошибки: `404 LESSON_NOT_FOUND`.

### 7.3 `PATCH` / `DELETE /lessons/{id}`
`owner+ADMIN` · `200` / `204`. Удаление последнего урока в модуле опубликованного курса → `409 PUBLISHED_COURSE_REQUIRES_CONTENT` (та же логика, что §6.4).

### 7.4 `PUT /modules/{moduleId}/lessons/order`
Полностью аналогично §6.5, для `UNIQUE(module_id, order_index)`.

### 7.5 `POST /lessons/{id}/complete`
Доступ: записанный студент · `200`

Отмечает урок пройденным и **пересчитывает** `progressPercent` записи как долю пройденных уроков курса.

**Решение.** Это альтернатива ручному `PATCH /enrollments/{id}/progress`, где студент сам присылает число. Ручной ввод прогресса — дыра в логике: клиент может отправить `100` не открыв ни одного урока, и `COMPLETED` вместе с сертификатом выдастся честно, по правилам. Отметка уроков делает прогресс производной от фактов, а не декларацией.

Требует таблицу `lesson_completions(enrollment_id, lesson_id, completed_at)` с составным PK — по сути ещё одна связь «многие ко многим с данными», ровно того же вида, что `Enrollment` и `Review` (§3.1 основного ТЗ). Поэтому вынесено в расширение: концептуально ничего нового не демонстрирует, объём работы добавляет.

Ошибки: `403 NOT_ENROLLED`, `404`, `409 ENROLLMENT_CANCELLED`.

## 8. Записи на курс

### 8.1 `POST /courses/{id}/enroll`
Доступ: `auth` (любая роль, кроме автора этого курса) · `201` или `200`

Тело пустое.

Проверки по порядку:

| # | Условие | Ошибка |
|---|---|---|
| 1 | курс существует | `404 COURSE_NOT_FOUND` |
| 2 | курс `PUBLISHED` | `409 COURSE_NOT_PUBLISHED` |
| 3 | зритель — не автор курса | `409 CANNOT_ENROLL_IN_OWN_COURSE` |
| 4 | нет активной записи | `409 ALREADY_ENROLLED` |

**Повторная запись после отмены.** Если запись существует в статусе `CANCELLED`, новая строка **не создаётся** — существующая возвращается в `ACTIVE` с сохранением прогресса, ответ `200` вместо `201`.

Так требует схема: `UNIQUE(student_id, course_id)` (§3.2 основного ТЗ) физически запрещает вторую строку. Обойти это можно было бы, добавив `status` в уникальный ключ, но тогда потерялась бы защита от двойной записи, ради которой ограничение и вводилось. Реактивация существующей строки сохраняет и инвариант, и историю, и прогресс студента, который вернулся к обучению.

**Гонка.** Два одновременных запроса на запись проходят проверку №4 оба и оба доходят до `INSERT`. Второй ловит `DataIntegrityViolationException` от `UNIQUE` — сервис перехватывает и возвращает `409 ALREADY_ENROLLED`. Проверка в коде даёт понятную ошибку в 99.9% случаев, ограничение в базе закрывает оставшиеся 0.1%. Без обработчика на исключение пользователь получит `500` — то есть ограничение сработает, а API соврёт о причине.

Ответ:

```json
{
  "id": 555, "courseId": 42, "courseTitle": "Spring Boot с нуля",
  "status": "ACTIVE", "progressPercent": 0,
  "enrolledAt": "2026-08-21T10:15:30Z", "completedAt": null
}
```

Побочный эффект: событие `enrollment.created`.

### 8.2 `GET /enrollments/my`
`auth` · `200` · Пагинация. Фильтр `?status=ACTIVE|COMPLETED|CANCELLED`, `sort`: `enrolledAt`, `progressPercent`.

Загрузка курсов — через `JOIN FETCH`, иначе на 20 записей уходит 21 запрос: канонический N+1, который §7 основного ТЗ обещает контролировать по логу `org.hibernate.SQL`.

### 8.3 `GET /enrollments/{id}`
Владелец записи или автор курса · `200` · `403 ACCESS_DENIED`, `404`.

### 8.4 `PATCH /enrollments/{id}/progress`
Владелец записи · `200`

```json
{ "progressPercent": 75 }
```

| Правило | Ошибка |
|---|---|
| 0..100 | `400 VALIDATION_ERROR` |
| запись не `CANCELLED` | `409 ENROLLMENT_CANCELLED` |
| прогресс не уменьшается | `409 PROGRESS_CANNOT_DECREASE` |
| запись не `COMPLETED` | `409 ENROLLMENT_COMPLETED` |

**Монотонность прогресса.** Уменьшение прогресса запрещено сознательно: «пройдено 80%» — это факт о прошлом, он не перестаёт быть правдой. Разрешив откат, мы получаем возможность бесконечно перевыдавать событие `enrollment.completed` (100 → 50 → 100 → …), а вместе с ним — сертификаты и письма. Правило на входе дешевле дедупликации на всех консьюмерах.

При достижении 100: `status = COMPLETED`, `completedAt = now()`, публикуется `enrollment.completed`.

### 8.5 `POST /enrollments/{id}/cancel`
Владелец записи · `200`

Строка не удаляется — `status = CANCELLED` (§4.3 основного ТЗ). `COMPLETED` не отменяется → `409 CANNOT_CANCEL_COMPLETED`: завершённое обучение — исторический факт, а не текущее состояние. Повторная отмена → `409 ENROLLMENT_ALREADY_CANCELLED`.

Отзыв, оставленный до отмены, **не удаляется**: студент действительно проходил курс, его мнение остаётся валидным.

### 8.6 `GET /enrollments/{id}/certificate`
Владелец записи · `200` или `202`

| Ситуация | Ответ |
|---|---|
| сертификат сгенерирован | `200` + `{ "url": "...", "issuedAt": "..." }` |
| генерация в очереди | `202` + `{ "status": "PENDING", "retryAfter": 5 }` |
| запись не `COMPLETED` | `409 ENROLLMENT_NOT_COMPLETED` |

**Классический пример асинхронной операции в синхронном API.** Генерация PDF занимает секунды и не должна держать HTTP-поток. `202` — это честный ответ «принято, но ещё не готово», а не ошибка; клиент опрашивает эндпоинт до `200`. Альтернативы — вебхук или SSE-канал; для портфолио polling нагляднее и проще проверяется.

## 9. Отзывы

### 9.1 `GET /courses/{id}/reviews`
`public` · `200` · Пагинация. Фильтр `?rating=5`, `sort`: `createdAt` (по умолчанию), `rating`.

Скрытые модератором отзывы (§9.6) в выдачу **не попадают** и в `AVG` не учитываются — ни для кого, включая автора отзыва. Показывать автору его скрытый отзыв как обычный означало бы, что он никогда не узнает о модерации и будет считать, что всё в порядке.

### 9.2 `GET /courses/{id}/reviews/summary`
`public` · `200`

```json
{
  "courseId": 42, "ratingAvg": 4.7, "ratingCount": 128,
  "histogram": { "1": 2, "2": 3, "3": 12, "4": 41, "5": 70 }
}
```

Один запрос с `GROUP BY rating`, а не пять `COUNT`.

### 9.3 `POST /courses/{id}/reviews`
Записанный студент · `201`

```json
{ "rating": 5, "body": "Отличный курс, всё разложено по полочкам." }
```

`rating` — `@Min(1) @Max(5)`; `body` — `@NotBlank`, 10..5000.

| Проверка | Ошибка |
|---|---|
| есть запись на курс | `403 NOT_ENROLLED` |
| запись не `CANCELLED` | `409 ENROLLMENT_CANCELLED` |
| отзыва ещё нет | `409 REVIEW_ALREADY_EXISTS` |

**Разночтение в основном ТЗ, требующее решения.** §2 говорит «пройдя курс, студент может оставить отзыв», §4.4 — «оставить отзыв может только студент с записью на этот курс». Это разные правила: первое требует `COMPLETED`, второе — любой активной записи.

Принято мягкое: достаточно записи в статусе `ACTIVE` или `COMPLETED`. Требование 100% прогресса означало бы, что отзыв «бросил на третьем уроке, потому что звук ужасный» невозможен — а это ровно тот отзыв, который нужен будущим студентам больше всех остальных. Строгий вариант включается флагом `learnhub.reviews.require-completion=true`, правило покрыто тестом в обеих конфигурациях.

Побочный эффект: событие `review.created` → пересчёт `rating_avg`/`rating_count`.

### 9.4 `PATCH /reviews/{id}`
Только автор отзыва, **без ADMIN** · `200`

Меняются `rating` и `body`. Проставляется `updatedAt` — клиент показывает «изменено».

**Решение.** §5 основного ТЗ разрешал PATCH автору **или** админу. Здесь сужено: админ, редактирующий текст чужого отзыва, — это подделка мнения под чужим именем. Инструменты модерации у админа другие: скрыть (§9.6) или удалить (§9.5). Разделение «автор владеет содержанием, модератор — видимостью» и понятнее, и безопаснее.

Ошибки: `403 NOT_REVIEW_AUTHOR`, `404`.

### 9.5 `DELETE /reviews/{id}`
Автор отзыва или `ADMIN` · `204`. Пересчёт рейтинга через событие `review.deleted`.

### 9.6 `POST /reviews/{id}/hide` · `POST /reviews/{id}/unhide`
`ADMIN` · `200`

```json
{ "reason": "Оскорбления в адрес автора курса" }
```

`reason` — `@NotBlank`, ≤ 500. Скрытие ставит `hidden = true`, `hidden_reason`, `hidden_by`, `hidden_at` (§21.1) и публикует `review.hidden` для пересчёта рейтинга.

**Скрытие вместо удаления.** Удалённый отзыв не оставляет следов: непонятно, кто удалил, за что и был ли он вообще. При споре «мой отзыв пропал» отвечать нечем. Флаг сохраняет и текст, и решение модератора, и авторство решения, и позволяет откатить его одним запросом. Это тот же принцип, по которому `Enrollment` не удаляется при отмене (§4.3 основного ТЗ) — состояние меняется, история остаётся.

### 9.7 `GET /reviews/my`
`auth` · `200` · Пагинация. Свои отзывы, включая скрытые (с `hidden: true` и причиной).

## 14. Каталог схем ответов

Схемы определены один раз и переиспользуются. Причина не в экономии букв: когда «курс» описан в трёх местах, эти три описания расходятся на четвёртом спринте, и клиент получает `ratingAvg` в каталоге и `rating` в карточке.

### 14.1 Правила, общие для всех ответов

| Правило | Почему так |
|---|---|
| Поле всегда присутствует, отсутствующее значение — `null` | клиент пишет `x.field === null`, а не `'field' in x`; исчезающие поля ломают типизацию на фронте |
| Пустая коллекция — `[]`, никогда не `null` | `null` заставляет проверять перед каждым перебором; `[]` перебирается ноль раз и не падает |
| `204` — тело пустое, не `{}` | «нет содержимого» означает нет содержимого |
| Даты — ISO-8601 в UTC с `Z` | соответствует `TIMESTAMPTZ` и `Instant` (§3.3 основного ТЗ) |
| Идентификаторы — числа, не строки | `BIGINT` укладывается в `Number` до 2^53, до этого предела проект не дойдёт |
| Деньги — **строка** | см. ниже |
| Перечисления — строки в UPPER_SNAKE | `"PUBLISHED"`, не `1`: числовой код нечитаем в логах и ломается при вставке значения в середину enum |

**Про деньги отдельно.** `price` отдаётся строкой: `"4990.00"`, а не `4990.00`.

`BigDecimal` Jackson по умолчанию сериализует числом, и на этом всё выглядит нормально ровно до JavaScript-клиента: `JSON.parse` кладёт значение в `double`, и `4990.00` становится `4990`, а `0.1 + 0.2` — известным `0.30000000000000004`. Тот самый аргумент, по которому в базе выбран `NUMERIC(10,2)`, а не `FLOAT` (§3.3 основного ТЗ), действует и на границе API: точность теряется не там, где её потеряли, а там, где её перестали защищать. Строка переносит десятичное значение без интерпретации, клиент разбирает её десятичной библиотекой.

Включается через `spring.jackson.json.write.write-numbers-as-strings` для конкретного поля либо `@JsonFormat(shape = STRING)` на нём. Второе точнее: строками становится цена, а не все числа подряд.

`ratingAvg` при этом остаётся числом — это статистика для отображения, а не сумма к оплате, и потеря знака после запятой в четвёртом разряде на неё не влияет.

### 14.2 Служебные обёртки

**`Page<T>`** (§0.4)

| Поле | Тип | Описание |
|---|---|---|
| `content` | `T[]` | элементы страницы, `[]` если пусто |
| `page.number` | `int` | номер, с нуля |
| `page.size` | `int` | запрошенный размер |
| `page.totalElements` | `long` | всего элементов с учётом фильтров |
| `page.totalPages` | `int` | всего страниц |

`totalElements` требует отдельного `COUNT(*)` с теми же условиями — на больших выборках это второй по стоимости запрос страницы. Если каталог вырастет, штатный выход — keyset-пагинация (`WHERE id < :lastId`) без общего счётчика, ценой отказа от прыжка на произвольную страницу.

**`Error`** (§0.8) — `timestamp`, `status`, `error`, `message`, `path`, `details[]?`, `traceId?`.

### 14.3 Пользователи

**`UserPrivate`** — только владельцу (`/users/me`, ответ регистрации)

| Поле | Тип | Null | Описание |
|---|---|:---:|---|

| `email` | `string` | | только в собственном профиле |
| `role` | `enum` | | `STUDENT` \| `INSTRUCTOR` \| `ADMIN` |
| `profile.firstName` | `string` | | |
| `profile.lastName` | `string` | | |

| `profile.avatarUrl` | `string` | ✓ | |

**`UserPublic`** — всем (`/users/{id}`)

**Без `email`.** Разница между `UserPrivate` и `UserPublic` — ровно одно поле, и соблазн обойтись одной схемой с «ну кто там будет читать email» велик. Одна схема означает, что `GET /users/1..N` выгружает адресную базу платформы. Две схемы — это одно поле в MapStruct-маппере против инцидента с персональными данными.

**`UserAdmin`** — `UserPublic` + `email`, `blocked` (`bool`), `blockedReason` (`string?`), `coursesCount`, `enrollmentsCount`, `lastLoginAt` (`instant?`).

**`AuthTokens`**

| Поле | Тип | Описание |
|---|---|---|
| `accessToken` | `string` | JWT |
| `refreshToken` | `string` | JWT |
| `tokenType` | `string` | всегда `"Bearer"` |
| `expiresIn` | `int` | секунды жизни access-токена |

`expiresIn` — именно секунды, а не абсолютная дата истечения: часы клиента расходятся с сервером на минуты, и токен, «истекающий» по локальному времени, обновляется либо слишком рано, либо слишком поздно. Относительная длительность от расхождения часов не зависит.

### 14.4 Категории

**`Category`**: `id` (`long`), `name` (`string`), `coursesCount` (`int`, только опубликованные курсы).

`coursesCount` считается одним `GROUP BY` для всего списка, а не подзапросом на строку — иначе `GET /categories` из тридцати категорий даёт тридцать один запрос: N+1 в самом безобидном на вид эндпоинте.

**`CourseListItem`** — элемент каталога

### 14.9 Уведомления

**`Notification`**: `id`, `type` (`enum`), `title`, `body`, `payload` (`object` — форма зависит от `type`), `readAt` (`instant?`), `createdAt`.

Объект, а не голое число `7`. Число — тупик: добавить рядом `hasImportant` или `oldestUnreadAt` можно только сломав контракт. Объект расширяется без изменения существующих клиентов, и лишние 12 байт того стоят.

**`payload` по типам:**

| `type` | `payload` |
|---|---|
| `COURSE_PUBLISHED` | `{ courseId, courseTitle, authorId }` |
| `COURSE_ARCHIVED` | `{ courseId, courseTitle }` |
| `ENROLLMENT_CREATED` | `{ courseId, courseTitle, enrollmentId }` |
| `NEW_STUDENT` | `{ courseId, studentId, studentName }` |
| `ENROLLMENT_COMPLETED` | `{ courseId, enrollmentId, certificateAvailable }` |

`title` и `body` формируются **на бэкенде при обработке события** и хранятся готовыми (§21.1). Альтернатива — отдавать клиенту `type` + `payload` и собирать текст на фронте — на первый взгляд гибче: локализация, изменение формулировок без миграции. На деле она даёт разъезжающиеся тексты в вебе и мобильном приложении и требует, чтобы каждый клиент знал все типы уведомлений. Готовый текст на сервере — один источник формулировок; `payload` остаётся для навигации по клику, а не для сборки строки.

### 14.10 Администрирование

**`OutboxMessage`**: `id`, `eventId` (`uuid`), `eventType`, `routingKey`, `createdAt`, `publishedAt` (`instant?`), `attempts` (`int`), `lastError` (`string?`), `ageSeconds` (`int` — возраст неопубликованного).

Полное тело — по `GET /admin/outbox/{id}`, и это отдельный запрос ровно потому, что он отдаёт больше, чем нужно для беглого просмотра очереди.

### 14.12 Что из этого проверяется тестами

Схемы ответов — не украшение спецификации, у них есть исполняемая проверка. В `@WebMvcTest` (§8 основного ТЗ) на каждую схему:

- обязательные поля присутствуют и не `null`;
- **запрещённые поля отсутствуют** — `passwordHash` нигде, `email` в `UserPublic`, `content` урока в `CourseDetail`, `hiddenReason` для постороннего;
- пустая коллекция сериализуется в `[]`;
- `price` — строка, а не число;
- даты оканчиваются на `Z`.

Второй пункт — главный. Тесты на присутствие полей ловят недоделанный маппинг, тесты на отсутствие ловят утечку, а утечка добавляется одной строкой в маппере и не проявляется никак, пока кто-нибудь не откроет DevTools.

# ЧАСТЬ II. АСИНХРОННАЯ ОБРАБОТКА: RabbitMQ

## 15. Зачем брокер в этом проекте

Без брокера `POST /courses/{id}/enroll` выглядит так: открыть транзакцию → создать запись → отправить письмо студенту → отправить уведомление автору → пересчитать статистику → закоммитить → ответить `201`.

Четыре проблемы, каждая из которых проявляется в проде:

1. **Время ответа определяется самым медленным шагом.** SMTP отвечает 300 мс — клиент ждёт 300 мс ради письма, которое ему не нужно в этот момент.
2. **Падение второстепенного ломает главное.** SMTP недоступен → исключение → откат транзакции → студент не записан, потому что не отправилось письмо. Приоритеты перевёрнуты.
3. **Транзакция держится на время внешнего вызова.** Соединение из пула занято, блокировки строк живут, пока мы ждём чужой сервер. При всплеске нагрузки пул исчерпывается и ложится весь сервис — не потому, что база не справилась, а потому что тормозил SMTP.
4. **Сервис записи знает про почту, PDF и статистику.** Каждая новая реакция на событие — правка `EnrollmentService`. Он растёт линейно от числа побочных эффектов.

Брокер разрывает эту связку: сервис публикует факт «студент записался» и отвечает `201`. Кто и как отреагирует — не его дело.

**Что RabbitMQ решает здесь, а что нет.** Он не «ускоряет» систему — суммарная работа та же. Он переносит её за границу HTTP-ответа и делает отказ второстепенного консьюмера безвредным для основного сценария. Взамен приходит **согласованность в конечном счёте**: между записью на курс и письмом проходит время, и это время надо признавать в UI, а не притворяться, что его нет.

**Почему RabbitMQ, а не Kafka.** Здесь — очередь задач с относительно небольшим потоком, где нужны гибкая маршрутизация по типу события, per-message ack, DLQ из коробки и приоритеты. Kafka — распределённый лог: сильна там, где нужны реплей истории, партиционирование по ключу и сотни тысяч событий в секунду, и заметно тяжелее в эксплуатации. Для «отправить письмо и пересчитать рейтинг» модель RabbitMQ подходит лучше и по инфраструктуре, и по объёму кода.

## 16. Дополнение к стеку

| Компонент | Версия | Артефакт |
|---|---|---|
| Брокер | RabbitMQ 4.x | образ `rabbitmq:4-management` |
| Интеграция | Spring AMQP 4.x | `spring-boot-starter-amqp` (имя стартера в Boot 4 не менялось) |
| Тесты | Testcontainers | `org.testcontainers:rabbitmq` |
| Тесты | Spring AMQP Test | `spring-rabbit-test` |
| Ожидания в тестах | Awaitility | `org.awaitility:awaitility` |

**Три подводных камня Boot 4 / Spring AMQP 4.**

1. **`Jackson2JsonMessageConverter` объявлен deprecated for removal начиная с 4.0.** Замена — `JacksonJsonMessageConverter` на Jackson 3. Аналогично `DefaultJackson2JavaTypeMapper` → `DefaultJacksonJavaTypeMapper`. Копирование конфигов из туториалов под Boot 3 даст предупреждения компилятора сегодня и не соберётся после удаления API.
2. **Jackson 3 сменил пакеты**: `com.fasterxml.jackson.databind` → `tools.jackson.databind`. Исключение — аннотации, они остались в `com.fasterxml.jackson.annotation`, поэтому `@JsonProperty` и `@JsonIgnore` в импортах не меняются, а `ObjectMapper` — меняется.
3. **JJWT и Jackson 3 конфликтуют.** JJWT 0.12.x тянет Jackson 2; в проекте на Boot 4 это даёт конфликт версий. Известные обходы — заменить `jjwt-jackson` на `jjwt-gson` либо явно подключить `spring-boot-jackson2` рядом. Проверить на своей версии до этапа 5, а не после.

## 17. Границы: что уходит в асинхрон, а что нет

Правило простое и проверяемое: **асинхронно то, отсутствие чего в момент ответа клиент не замечает.**

| Уходит в очередь | Остаётся синхронным |
|---|---|
| Email- и in-app-уведомления | Создание записи на курс |
| Генерация сертификата | Проверка бизнес-правил |
| Пересчёт `rating_avg` / `enrollment_count` | Смена статуса курса |
| Индексация курса для поиска | Валидация и авторизация |
| Аналитические события | Всё, что влияет на код ответа |

**Антипример, о который спотыкаются регулярно.** «Отправим создание записи в очередь, ответим `202`, обработаем фоном». Тогда проверки `ALREADY_ENROLLED` и `COURSE_NOT_PUBLISHED` происходят **после** ответа клиенту, и сообщить о них некому: `202` уже ушёл. Валидация должна возвращать код ответа, значит остаётся синхронной. В очередь идут следствия, а не решения.

## 18. Каталог событий

Routing key — `<агрегат>.<событие>`, прошедшее время: событие описывает свершившийся факт, а не команду. `enrollment.created`, а не `create.enrollment` — консьюмер не обязан подчиняться, он ставится в известность.

| Routing key | Публикуется | Payload | Кто слушает |
|---|---|---|---|
| `user.registered` | `POST /auth/register` | `userId`, `email`, `firstName` | email |
| `course.published` | `POST /courses/{id}/publish` | `courseId`, `authorId`, `title` | email, in-app, search |
| `course.archived` | `POST /courses/{id}/archive` | `courseId`, `authorId`, `title` | email, in-app, search |
| `course.updated` | `PATCH /courses/{id}` | `courseId`, `changedFields` | search |
| `enrollment.created` | `POST /courses/{id}/enroll` | `enrollmentId`, `studentId`, `courseId`, `authorId` | email, in-app, stats |
| `enrollment.completed` | прогресс достиг 100 | `enrollmentId`, `studentId`, `courseId`, `completedAt` | email, in-app, certificates |
| `enrollment.cancelled` | `POST /enrollments/{id}/cancel` | `enrollmentId`, `studentId`, `courseId` | stats |
| `review.created` | `POST /courses/{id}/reviews` | `reviewId`, `courseId`, `authorId`, `rating` | in-app, stats |
| `review.updated` | `PATCH /reviews/{id}` | `reviewId`, `courseId`, `oldRating`, `newRating` | stats |
| `review.deleted` | `DELETE /reviews/{id}` | `reviewId`, `courseId`, `rating` | stats |
| `review.hidden` | `POST /reviews/{id}/hide` | `reviewId`, `courseId`, `rating` | stats, in-app |

**В payload — идентификаторы и минимум данных, не сущности.**

Отправлять `CourseResponse` целиком заманчиво: консьюмеру не придётся ходить в базу. Но сообщение живёт в очереди минуты или часы, и всё это время данные в нём устаревают. Консьюмер, отправляющий письмо «опубликован курс "Старое название"» через 20 минут после переименования, формально прав и фактически неверен. Плюс любое изменение DTO становится изменением контракта сообщений — с версионированием и совместимостью.

Исключение — поля, нужные для дедупликации или маршрутизации (`rating` в `review.deleted`: строки уже нет, из базы её не достать). Это осознанное исключение, а не общее правило.

### 19.1 Обменники и очереди

| Обменник | Тип | Назначение |
|---|---|---|
| `learnhub.events` | topic, durable | все доменные события |
| `learnhub.dlx` | topic, durable | приём отвергнутых сообщений |
| `learnhub.retry` | topic, durable | отложенная переотправка |

| Очередь | Binding | Что делает |
|---|---|---|
| `notifications.email` | `user.*`, `course.published`, `course.archived`, `enrollment.*` | письма |
| `notifications.inapp` | `course.*`, `enrollment.*`, `review.created` | строки в `notifications` |
| `stats.rating` | `review.*`, `enrollment.created`, `enrollment.cancelled` | `rating_avg`, `rating_count`, `enrollment_count` |
| `search.index` | `course.*` | переиндексация (заглушка до внедрения поиска) |
| `certificates` | `enrollment.completed` | генерация PDF |

**Почему topic, а не direct.** Topic позволяет консьюмеру подписаться на `course.*` одной привязкой и автоматически получать события, которых ещё не существует. С direct-обменником каждое новое событие требует правки конфигурации каждого заинтересованного консьюмера — то самое связывание, ради устранения которого брокер и ставился.

**Почему очередь на консьюмера, а не одна общая.** Отдельные очереди дают независимые счётчики, независимые DLQ и независимое масштабирование. С одной общей очередью упавшая генерация PDF блокирует отправку писем — консьюмеры делят одну голову очереди. Кроме того, при `basic.ack` в общей очереди неясно, кто именно обработал сообщение; в pub/sub каждый подписчик должен получить **свою копию**, а это ровно «своя очередь на подписчика».

### 19.2 Dead letter и повторы

Каждая рабочая очередь объявляется quorum-очередью с двумя аргументами:

```java
QueueBuilder.durable("notifications.email")
        .quorum()
        .deliveryLimit(5)
        .deadLetterExchange("learnhub.dlx")
        .deadLetterRoutingKey("notifications.email")
        .build();
```

- `deliveryLimit(5)` — после пятой неудачной доставки сообщение уходит в DLX автоматически, без ручного подсчёта попыток.
- `deadLetterExchange` — куда именно.

**Самая дорогая ошибка при первом знакомстве с RabbitMQ.** По умолчанию `spring.rabbitmq.listener.simple.default-requeue-rejected = true`: отвергнутое сообщение возвращается в голову очереди. Если оно падает из-за собственного содержимого — битый JSON, ссылка на удалённого пользователя — оно будет падать вечно. Получается цикл на сотни тысяч попыток в минуту: логи растут гигабайтами, консьюмер занят только этим сообщением, остальная очередь стоит. Отсюда `default-requeue-rejected: false` — обязательная строка конфигурации, а не тонкая настройка.

**Отложенный повтор.** Мгновенный повтор бессмыслен, когда причина — недоступный SMTP: пять попыток за 50 мс упрутся в ту же недоступность. Схема с задержкой:

```
рабочая очередь ──(reject)──► learnhub.dlx ──► retry.<queue> (TTL 30s, без консьюмеров)
                                                      │  истёк TTL
                                                      ▼
                                        dead-letter обратно в learnhub.events
```

Очередь ожидания без консьюмеров — сообщение лежит, пока не истечёт `x-message-ttl`, после чего дедлеттерится обратно в рабочую. Ограничение подхода: TTL задаётся на очередь, поэтому задержка фиксированная. Экспоненциальная выдержка требует лестницы очередей (`retry.30s`, `retry.5m`, `retry.30m`) с маршрутизацией по счётчику попыток в заголовке — либо плагина `rabbitmq_delayed_message_exchange`. Для проекта достаточно одноступенчатой схемы с явно описанным ограничением.

**Локальный retry Spring (`listener.simple.retry.enabled`) — не замена.** Он повторяет в том же потоке, блокируя консьюмера на время всех попыток, и не переживает рестарт приложения. Полезен против мгновенных сбоев (дедлок в базе), бесполезен против недоступности внешнего сервиса на десять минут.

### 19.3 Консьюмер `stats.rating` — почему он существует

Этот консьюмер — прямой ответ на проблему из §5.2: сортировка каталога по рейтингу и популярности.

```
review.created ─► stats.rating ─► UPDATE courses
                                  SET rating_avg = (SELECT AVG(rating) FROM reviews
                                                    WHERE course_id = ? AND hidden = false),
                                      rating_count = (SELECT COUNT(*) ...)
                                  WHERE id = ?
```

**Пересчёт агрегатом, а не инкремент.** Инкрементальный вариант (`rating_avg = (rating_avg * n + new) / (n+1)`) быстрее и хрупче: любая потеря или дублирование сообщения навсегда искажает значение без возможности заметить. Полный пересчёт по `AVG` идемпотентен по построению — повторная обработка того же сообщения даёт тот же результат, и `processed_events` для него, строго говоря, не обязателен. Цена — один агрегирующий запрос по индексу `reviews(course_id)` вместо арифметики, что несопоставимо дешевле расследования «почему у курса рейтинг 7.3».

§3.3 основного ТЗ говорил: денормализация «вводится осознанно, если станет узким местом». Узкое место названо — сортировка каталога по вычисляемому полю. `AVG` остаётся источником истины, денормализованные колонки — его кэшем с известной задержкой в сотни миллисекунд. В карточке курса (`GET /courses/{id}`) рейтинг можно считать на лету, если требуется точность момента.

## 20. Надёжность доставки

### 20.1 Публикация и транзакция

Ошибка, которую делают почти все:

```java
@Transactional
public EnrollmentResponse enroll(Long courseId, Long studentId) {
    Enrollment saved = repository.save(new Enrollment(...));
    rabbitTemplate.convertAndSend(EXCHANGE, "enrollment.created", event);  // ❌
    return mapper.toResponse(saved);
}
```

Здесь два хранилища меняются без общей транзакции. Возможен любой из исходов:

- Сообщение ушло, транзакция откатилась → консьюмер получает `enrollmentId`, которого в базе нет. Письмо о несуществующей записи.
- Транзакция закоммитилась, брокер недоступен → запись есть, письма не будет никогда.

Распределённые транзакции (XA) решают это ценой, несоразмерной задаче.

### 20.2 Два рабочих решения

**Вариант А — публикация после коммита.**

```java
@Component
class EnrollmentEventPublisher {

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void on(EnrollmentCreatedEvent event) {
        rabbitTemplate.convertAndSend(EXCHANGE, "enrollment.created", event);
    }
}
```

Сервис публикует Spring-событие внутри транзакции, отправка в брокер происходит после успешного коммита. Пятнадцать строк, никаких новых таблиц.

Остаточный риск: коммит прошёл, а брокер лёг в интервале между коммитом и отправкой — сообщение теряется молча. Это **at-most-once**: ложных событий нет, потери возможны. Для писем приемлемо, для списания денег — нет.

**Вариант Б — transactional outbox.**

```
   ┌─ одна транзакция ───────────────────────────┐
   │  INSERT INTO enrollments ...                 │
   │  INSERT INTO outbox_messages (payload, ...)  │
   └──────────────────────────────────────────────┘
                      │ COMMIT
                      ▼
   Публикатор (@Scheduled, каждую секунду):
     SELECT * FROM outbox_messages
      WHERE published_at IS NULL
      ORDER BY id LIMIT 100
        FOR UPDATE SKIP LOCKED
     → отправить в RabbitMQ
     → UPDATE published_at = now()
```

Сообщение и данные пишутся одной транзакцией в одну базу — либо есть оба, либо ни одного. Публикатор доставит сообщение, даже если брокер был недоступен час: строки просто дождутся своей очереди. Это **at-least-once** — возможна повторная отправка (отправили, упали до `UPDATE`), поэтому нужна идемпотентность консьюмеров (§20.4).

`FOR UPDATE SKIP LOCKED` — ключевая деталь: без неё два экземпляра приложения выберут одни и те же строки и отправят каждое сообщение дважды. `SKIP LOCKED` заставляет второй экземпляр пропустить заблокированные строки и взять следующие — очередь распараллеливается без внешней координации.

**Что выбрать.** Оба, последовательно: вариант А на этапе 10, вариант Б на этапе 11. Так в истории коммитов видно и понимание проблемы, и переход к решению — это интереснее для разбора на собеседовании, чем сразу готовый outbox без объяснения, зачем он.

### 20.3 Publisher confirms

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
    template:
      mandatory: true
```

- **Confirms** — брокер подтверждает приём сообщения. Без них `convertAndSend` возвращает управление сразу и не знает, дошло ли; при варианте Б без confirm'ов `published_at` проставится для недоставленного сообщения.
- **Returns + mandatory** — сообщение, не попавшее ни в одну очередь, возвращается отправителю, а не исчезает. Ловит опечатку в routing key: без этого сообщения молча растворяются в обменнике, и отладка «письма не приходят» занимает часы.

### 20.4 Идемпотентность консьюмеров

At-least-once означает, что консьюмер обязан выдерживать повторы. Два пути:

**Естественная идемпотентность** — предпочтительна, когда достижима. `UPDATE courses SET rating_avg = (SELECT AVG(...))` можно выполнить сто раз с одним результатом. Ничего дополнительно не нужно.

**Дедупликация по `eventId`** — когда операция по природе не идемпотентна (отправка письма, вставка уведомления):

```java
@RabbitListener(queues = "notifications.inapp")
@Transactional
public void handle(DomainEvent<?> event) {
    if (!processedEvents.markProcessed(event.eventId(), "notifications.inapp")) {
        return;                       // уже обрабатывали — тихо выходим
    }
    notificationService.create(...);
}
```

`markProcessed` — `INSERT ... ON CONFLICT DO NOTHING`, возвращает, вставилась ли строка. Проверка и работа — в одной транзакции: иначе между «проверил» и «выполнил» второй консьюмер сделает то же самое.

`consumer` в составе ключа обязателен: одно событие обрабатывают несколько консьюмеров, и `eventId` в качестве PK заставил бы их конкурировать. PK — `(event_id, consumer)`.

Строки старше 30 дней удаляются по расписанию: таблица дедупликации без очистки растёт быстрее основных данных.

### 20.5 Prefetch и конкурентность

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 10
        concurrency: 2
        max-concurrency: 5
        default-requeue-rejected: false
        acknowledge-mode: auto
```

- **`prefetch`** — сколько неподтверждённых сообщений консьюмер держит у себя. Без ограничения (`0`) один консьюмер вытянет всю очередь в память, а второй экземпляр останется без работы: балансировка ломается, память течёт. Ориентир — 10–20 для быстрых обработчиков, 1–5 для медленных.
- **`acknowledge-mode: auto`** — Spring подтверждает после успешного возврата из метода и отвергает при исключении. Название вводит в заблуждение: это **не** `autoAck` протокола AMQP (который подтверждает при доставке и теряет сообщение при падении консьюмера). Ручной режим нужен, только когда ack зависит от логики внутри метода.

## 21. Изменения схемы БД

### 21.1 Миграция `V2__async_and_moderation.sql`

```sql
-- Модерация отзывов (§9.6)
ALTER TABLE reviews
    ADD COLUMN hidden        BOOLEAN     NOT NULL DEFAULT FALSE,
    ADD COLUMN hidden_reason TEXT,
    ADD COLUMN hidden_by     BIGINT      REFERENCES users(id) ON DELETE SET NULL,
    ADD COLUMN hidden_at     TIMESTAMPTZ,
    ADD COLUMN updated_at    TIMESTAMPTZ,
    ADD CONSTRAINT reviews_hidden_reason_required
        CHECK (hidden = FALSE OR hidden_reason IS NOT NULL);

-- Денормализованные агрегаты курса (§19.3)
ALTER TABLE courses
    ADD COLUMN rating_avg       NUMERIC(3,2) NOT NULL DEFAULT 0.00,
    ADD COLUMN rating_count     INTEGER      NOT NULL DEFAULT 0,
    ADD COLUMN enrollment_count INTEGER      NOT NULL DEFAULT 0,
    ADD CONSTRAINT courses_rating_avg_range CHECK (rating_avg BETWEEN 0 AND 5);

CREATE INDEX idx_courses_catalog_rating
    ON courses (rating_avg DESC, id) WHERE status = 'PUBLISHED';
CREATE INDEX idx_courses_catalog_popularity
    ON courses (enrollment_count DESC, id) WHERE status = 'PUBLISHED';

ALTER TABLE enrollments ADD COLUMN completed_at TIMESTAMPTZ;

-- Refresh-токены (§2.2)
CREATE TABLE refresh_tokens (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token_hash  VARCHAR(64) NOT NULL UNIQUE,
    expires_at  TIMESTAMPTZ NOT NULL,
    revoked_at  TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_refresh_tokens_user ON refresh_tokens (user_id) WHERE revoked_at IS NULL;

-- Transactional outbox (§20.2)
CREATE TABLE outbox_messages (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_id     UUID        NOT NULL UNIQUE,
    event_type   VARCHAR(64) NOT NULL,
    routing_key  VARCHAR(128) NOT NULL,
    payload      JSONB       NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at TIMESTAMPTZ,
    attempts     INTEGER     NOT NULL DEFAULT 0,
    last_error   TEXT
);
CREATE INDEX idx_outbox_unpublished
    ON outbox_messages (id) WHERE published_at IS NULL;

-- Дедупликация на стороне консьюмеров (§20.4)
CREATE TABLE processed_events (
    event_id     UUID        NOT NULL,
    consumer     VARCHAR(64) NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (event_id, consumer)
);

-- In-app уведомления (§10)
CREATE TABLE notifications (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id    BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    type       VARCHAR(64) NOT NULL,
    title      VARCHAR(255) NOT NULL,
    body       TEXT        NOT NULL,
    payload    JSONB       NOT NULL DEFAULT '{}'::jsonb,
    read_at    TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_notifications_user_created ON notifications (user_id, created_at DESC);
CREATE INDEX idx_notifications_unread       ON notifications (user_id) WHERE read_at IS NULL;
```

Таблиц становится **14** (было 9).

**Три решения в этой миграции.**

- **Частичные индексы вместо обычных.** `idx_outbox_unpublished ... WHERE published_at IS NULL` покрывает только неотправленные строки — единицы или десятки против миллионов отправленных. Индекс остаётся крошечным независимо от возраста таблицы. То же для непрочитанных уведомлений и активных токенов. Это тот случай, когда индекс добавляется под конкретный известный запрос, а не «на всякий случай» (§3.3 основного ТЗ).
- **`JSONB` для `payload`, а не колонки под каждый тип.** У десяти типов уведомлений десять разных наборов полей; отдельные колонки дали бы разреженную таблицу с NULL'ами и `ALTER TABLE` на каждый новый тип. JSONB здесь на своём месте — в нём нет данных, по которым идёт поиск или соединение. Как только по полю внутри payload понадобится фильтрация, оно должно переехать в обычную колонку.
- **Хеш refresh-токена, а не сам токен.** Утечка дампа базы не должна давать возможность войти под любым пользователем. Токен хешируется SHA-256 (не bcrypt: токен и так случайный с высокой энтропией, растягивание не нужно, а скорость проверки важна).

### 21.2 Соответствие JPA

Денормализованные колонки на стороне сущности объявляются `insertable = false, updatable = false`. Их владелец — консьюмер, обновляющий строку прицельным `UPDATE`; если тот же курс окажется в персистентном контексте другого запроса, Hibernate при флаше перезапишет их устаревшими значениями из памяти. Явный запрет на запись снимает вопрос на уровне маппинга, а не дисциплины.

**Локальный retry и `deliveryLimit` работают вместе, а не вместо друг друга.** Первый гасит мгновенные сбои (дедлок, разрыв соединения с базой) тремя попытками за несколько секунд. Второй считает **доставки** — сообщение, исчерпавшее локальные попытки, возвращается в очередь и доставляется заново, и после пятой такой доставки уходит в DLQ. Итого до 15 фактических выполнений обработчика — это надо понимать, чтобы не удивляться количеству записей в логе.

### 22.2 Объявление топологии

```java
@Configuration
public class RabbitTopologyConfig {

    public static final String EVENTS = "learnhub.events";
    public static final String DLX    = "learnhub.dlx";
    public static final String RETRY  = "learnhub.retry";

    @Bean
    Declarables exchanges() {
        return new Declarables(
                ExchangeBuilder.topicExchange(EVENTS).durable(true).build(),
                ExchangeBuilder.topicExchange(DLX).durable(true).build(),
                ExchangeBuilder.topicExchange(RETRY).durable(true).build()
        );
    }

    @Bean
    Declarables emailQueue() {
        Queue main = QueueBuilder.durable("notifications.email")
                .quorum()
                .deliveryLimit(5)
                .deadLetterExchange(DLX)
                .deadLetterRoutingKey("notifications.email")
                .build();

        Queue dlq = QueueBuilder.durable("notifications.email.dlq").quorum().build();

        return new Declarables(
                main, dlq,
                BindingBuilder.bind(main).to(new TopicExchange(EVENTS)).with("user.*"),
                BindingBuilder.bind(main).to(new TopicExchange(EVENTS)).with("course.published"),
                BindingBuilder.bind(main).to(new TopicExchange(EVENTS)).with("course.archived"),
                BindingBuilder.bind(main).to(new TopicExchange(EVENTS)).with("enrollment.*"),
                BindingBuilder.bind(dlq).to(new TopicExchange(DLX)).with("notifications.email")
        );
    }
    // остальные очереди — аналогично
}
```

**Топология в коде, а не в rabbitmqadmin.** Объявленная бинами, она версионируется вместе с приложением, применяется автоматически при старте и одинаково поднимается в проде, локально и в Testcontainers. Ровно та же логика, по которой схемой базы владеет Flyway, а не `ddl-auto` (§6 основного ТЗ).

Осторожно: изменение аргументов существующей очереди приводит не к обновлению, а к `PRECONDITION_FAILED` при старте — RabbitMQ не переобъявляет очередь с другими параметрами. Очередь нужно удалять и создавать заново, что при живых сообщениях требует плана. Это цена декларативного подхода, о ней стоит знать до первого инцидента.

### 22.3 Конвертер сообщений

```java
@Configuration
public class RabbitMessagingConfig {

    @Bean
    MessageConverter messageConverter() {
        // Spring AMQP 4: Jackson2JsonMessageConverter объявлен deprecated for removal
        return new JacksonJsonMessageConverter("com.the0shail.course_api.messaging.event");
    }

    @Bean
    RabbitTemplate rabbitTemplate(ConnectionFactory cf, MessageConverter converter) {
        RabbitTemplate template = new RabbitTemplate(cf);
        template.setMessageConverter(converter);
        template.setConfirmCallback((correlation, ack, cause) -> {
            if (!ack) {
                log.error("Publish not confirmed: {} cause={}", correlation, cause);
            }
        });
        template.setReturnsCallback(returned ->
                log.error("Message returned: rk={} reply={}",
                        returned.getRoutingKey(), returned.getReplyText()));
        return template;
    }
}
```

**Про `__TypeId__` и доверенные пакеты.** Jackson-конвертер по умолчанию пишет полное имя Java-класса в заголовок `__TypeId__` и по нему десериализует на приёме. Отсюда два следствия:

- Список доверенных пакетов — **обязателен**. Конвертер, которому разрешено инстанцировать любой класс из заголовка сообщения, это удалённое выполнение кода через очередь. Конструктор без аргументов доверяет всему (`*`).
- Привязка к именам классов делает переименование пакета ломающим изменением: сообщения, уже лежащие в очереди, перестанут читаться после деплоя. Устойчивее — `DefaultClassMapper` с явным отображением `"enrollment.created" → EnrollmentCreatedEvent`: контракт становится строкой в конфиге, а не структурой пакетов.

### 22.4 Конверт события

```java
public record DomainEvent<T>(
        UUID eventId,
        String eventType,
        int version,
        Instant occurredAt,
        T payload
) {
    public static <T> DomainEvent<T> of(String type, T payload) {
        return new DomainEvent<>(UUID.randomUUID(), type, 1, Instant.now(), payload);
    }
}
```

| Поле | Зачем |
|---|---|
| `eventId` | дедупликация (§20.4), сквозная трассировка по логам |
| `eventType` | ветвление в консьюмере без разбора payload |
| `version` | совместимость при изменении структуры payload |
| `occurredAt` | момент факта, не момент доставки — консьюмер видит возраст сообщения |

`version` добавляется сразу, хотя пока всегда `1`. Добавить его потом — значит разбирать сообщения без поля версии, гадая, какая у них структура. Одно поле сейчас против ветвления в каждом консьюмере через полгода.

## 24. Тестирование асинхронной части

### 24.1 Публикация события

```java
@SpringBootTest
@Testcontainers
class EnrollmentEventPublishingTest {

    @Container
    @ServiceConnection
    static RabbitMQContainer rabbit = new RabbitMQContainer("rabbitmq:4-management");

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:17");

    @Test
    void enrollPublishesEvent() {
        enrollmentService.enroll(courseId, studentId);

        Object received = rabbitTemplate.receiveAndConvert("notifications.email", 5000);

        assertThat(received)
                .isInstanceOf(DomainEvent.class)
                .extracting("eventType").isEqualTo("enrollment.created");
    }
}
```

`@ServiceConnection` избавляет от ручного проброса `spring.rabbitmq.host` через `@DynamicPropertySource`.

### 24.2 Проверки, ради которых всё затевалось

| Что проверяем | Как |
|---|---|
| Событие публикуется **после коммита** | откатить транзакцию → убедиться, что очередь пуста |
| Сбой брокера не ломает основной сценарий | остановить контейнер → `enroll` возвращает `201` |
| Outbox переживает недоступность брокера | остановить, вызвать `enroll`, запустить → сообщение доставлено |
| Отравленное сообщение попадает в DLQ | консьюмер бросает исключение → сообщение в `*.dlq`, **не** в бесконечном цикле |
| Дубликат обрабатывается один раз | отправить одно сообщение дважды → одна строка в `notifications` |
| Рейтинг пересчитывается | создать отзыв → дождаться → `courses.rating_avg` обновлён |

Тест на DLQ — важнейший в списке. Он ловит `default-requeue-rejected: true` (§19.2), то есть ошибку конфигурации, которая при ручной проверке выглядит нормально и убивает сервис под нагрузкой.

### 24.3 Ожидание асинхронного результата

```java
await().atMost(Duration.ofSeconds(5))
       .pollInterval(Duration.ofMillis(100))
       .untilAsserted(() ->
           assertThat(courseRepository.findById(courseId))
                   .get()
                   .extracting(Course::getRatingAvg)
                   .isEqualTo(new BigDecimal("4.50")));
```

`Thread.sleep(2000)` в асинхронных тестах — источник и медленной сборки, и мигающих падений на загруженном CI. Awaitility опрашивает условие и завершается сразу после выполнения.

### 24.4 Тест консьюмера без брокера

Логика обработчика — обычный метод. Она тестируется юнит-тестом с замоканными зависимостями, `@RabbitListener` при этом не участвует. Testcontainers нужны для проверки **доставки и топологии**, не бизнес-логики: слишком дорогой инструмент, чтобы гонять через него каждое правило.

## 25. Наблюдаемость

| Что | Где |
|---|---|
| Глубина очередей, скорость, DLQ | Management UI, `localhost:15672` |
| Состояние соединения | `/actuator/health` (`RabbitHealthIndicator` включается автоматически) |
| Метрики Micrometer | `rabbitmq.consumed`, `rabbitmq.published`, `rabbitmq.rejected` |
| Возраст неотправленного outbox | своя метрика: `max(now() - created_at) WHERE published_at IS NULL` |

**Один сигнал важнее остальных: растущая глубина очереди.** Она означает, что публикуется быстрее, чем обрабатывается, и разрыв во времени между действием и его последствием увеличивается. Стабильная глубина в тысячи сообщений — это уведомления, приходящие через час.

**Health check требует осторожности.** `RabbitHealthIndicator` попадает в общий `/actuator/health`, а тот часто используется как readiness probe в Kubernetes. Тогда падение брокера выводит поды приложения из балансировки — то есть отказ второстепенного компонента останавливает основной сценарий, ровно то, от чего брокер должен был защитить (§15). Правильно — вынести Rabbit в `liveness`-независимую группу или исключить из readiness.

## 26. Чего делать не надо

| Антипаттерн | Почему плохо |
|---|---|
| Публикация внутри `@Transactional` | коммит и отправка не атомарны (§20.1) |
| Полные DTO в payload | данные устаревают в очереди, контракт становится хрупким (§18) |
| `default-requeue-rejected: true` | бесконечный цикл на отравленном сообщении (§19.2) |
| Одна очередь на всех консьюмеров | pub/sub требует копию каждому; падение одного блокирует остальных |
| Синхронное ожидание ответа консьюмера | это RPC поверх очереди, простой HTTP-вызов был бы честнее и проще |
| RabbitMQ как хранилище | очередь — транспорт; долгое хранение → память кончится или сообщения истекут по TTL |
| Расчёт на порядок сообщений между очередями | порядок гарантирован в пределах одной очереди с одним консьюмером, дальше — нет |
| Инкрементальные счётчики вместо пересчёта | одна потеря или дубль искажают значение навсегда (§19.3) |
| `Thread.sleep` в тестах | медленно и мигает на CI (§24.3) |

## 27. Обновлённая структура пакетов

```
com.the0shail.course_api
├── config
├── controller
├── dto
├── entity
├── exception
├── mapper
├── messaging                     ← новое
│   ├── config                    RabbitTopologyConfig, RabbitMessagingConfig
│   ├── event                     DomainEvent + payload-record'ы
│   ├── publisher                 EventPublisher, OutboxPublisher, OutboxScheduler
│   └── consumer                  EmailConsumer, InAppConsumer, RatingConsumer, ...
├── repository
├── security
└── service
```

`messaging` рядом со слоями, а не внутри них: это отдельная точка входа в приложение — такая же, как REST-контроллеры, только вход не HTTP. Раскладывать консьюмеры по `service` значило бы смешать «что делает система» с «как в неё попадает запрос».

Правило зависимостей: `service` знает о `messaging.event` и `messaging.publisher`, но не о `consumer`. Консьюмеры вызывают сервисы, обратной стрелки нет. Сервис, вызывающий консьюмер, — признак, что событие вообще не нужно было.

## 29. Дополнение к §10 основного ТЗ

Что добавляет асинхронная часть к тому, что проект показывает работодателю:

- **Событийная интеграция на практике**: топология topic-обменников, привязки по шаблону, DLQ, повторы с задержкой, quorum-очереди с `delivery-limit`.
- **Понимание проблемы двойной записи** — почему `save()` и `send()` в одном методе не атомарны, и два разных способа это закрыть с явным сравнением гарантий (at-most-once против at-least-once).
- **Идемпотентность как проектное требование**, а не как заплатка: где она достигается естественно, где нужна дедупликация по `eventId`.
- **Осознанная граница синхронного и асинхронного**: валидация возвращает код ответа и остаётся синхронной, следствия уходят в очередь.
- **Согласованность в конечном счёте** с названной ценой: денормализованные агрегаты отстают от источника истины, `AVG` остаётся правдой, лаг измерим и признан.
- **Тестирование распределённого поведения**: отравленное сообщение, дубликат, падение брокера — сценарии, которые обычно обнаруживаются в проде.
- **Диагностика знакомых граблей**: бесконечный requeue, потерянные сообщения без `mandatory`, RCE через `__TypeId__` без доверенных пакетов, брокер в readiness probe.
