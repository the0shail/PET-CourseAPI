# LearnHub API — техническое задание

REST API платформы онлайн-курсов. Учебно-портфолиный проект уровня middle Java-разработчика.

**Цель:** показать работу с множественными связями в JPA, слоистой архитектурой, безопасностью и тестами — не «ещё один CRUD», а система с бизнес-правилами, ограничениями целостности и осознанными техническими решениями.

## 2. Предметная область

Платформа онлайн-курсов. Три роли:

- **STUDENT** — просматривает каталог, записывается на курсы, проходит уроки, оставляет отзывы.
- **INSTRUCTOR** — всё вышеперечисленное плюс создаёт и публикует собственные курсы.
- **ADMIN** — модерация: управление категориями, доступ к чужим курсам, блокировка отзывов.

Курс состоит из модулей, модуль — из уроков. Курс проходит жизненный цикл `DRAFT → PUBLISHED → ARCHIVED`. Студент записывается на курс (`Enrollment`), запись хранит прогресс и статус. Пройдя курс, студент может оставить один отзыв.

## 3. Модель данных

### 3.1 Сущности и связи

| Связь | Тип | Комментарий |
|---|---|---|
| `User` — `UserProfile` | 1:1 | общий первичный ключ, `@MapsId` |
| `User` — `Course` | 1:N | пользователь как автор курса |
| `Course` — `Module` | 1:N | каскадное удаление |
| `Module` — `Lesson` | 1:N | каскадное удаление |
| `Course` — `Category` | M:N | чистая `@ManyToMany`, связь без своих данных |
| `User` — `Course` через `Enrollment` | M:N с данными | две `@ManyToOne`, у связи есть статус и прогресс |
| `User` — `Course` через `Review` | M:N с данными | две `@ManyToOne`, у связи есть рейтинг и текст |

**Ключевое решение проекта.** `Enrollment` и `Review` — это связи «многие ко многим», которые *нельзя* оформить как `@ManyToMany`. Как только у связи появляются собственные поля (когда записался, сколько прошёл, какой статус), соединительная таблица перестаёт быть служебной и становится полноценной сущностью с двумя `@ManyToOne` и собственным `id`. `@ManyToMany` остаётся только там, где связь ничего о себе не хранит — курс ↔ категория.

`User` участвует в связях в двух ролях одновременно: как автор курсов и как студент. Одна сущность — разные связи.

### 3.2 Таблицы

Всего 9 таблиц: 8 под сущности + `course_categories` (соединительная для `@ManyToMany`).

**`users`** — `id`, `email` (UNIQUE), `password_hash`, `role` (CHECK), `created_at`
**`user_profiles`** — `user_id` (PK = FK на users, ON DELETE CASCADE), `first_name`, `last_name`, `bio`, `avatar_url`
**`categories`** — `id`, `name` (UNIQUE)
**`courses`** — `id`, `author_id` (FK → users, ON DELETE RESTRICT), `title`, `description`, `price` NUMERIC(10,2), `status` (CHECK), `created_at`, `updated_at`
**`course_categories`** — `course_id`, `category_id`, составной PK
**`modules`** — `id`, `course_id` (FK, CASCADE), `title`, `order_index`, UNIQUE(`course_id`, `order_index`)
**`lessons`** — `id`, `module_id` (FK, CASCADE), `title`, `content`, `order_index`, UNIQUE(`module_id`, `order_index`)
**`enrollments`** — `id`, `student_id` (FK, CASCADE), `course_id` (FK, RESTRICT), `status` (CHECK), `progress_percent` (CHECK 0..100), `enrolled_at`, UNIQUE(`student_id`, `course_id`)
**`reviews`** — `id`, `author_id` (FK, CASCADE), `course_id` (FK, CASCADE), `rating` (CHECK 1..5), `body`, `created_at`, UNIQUE(`author_id`, `course_id`)

Полный DDL — в `V1__init_schema.sql`.

### 3.3 Решения по схеме и их обоснование

- **`NUMERIC(10,2)` для цены, не `FLOAT`.** Двоичная дробь не представляет 0.1 точно — на деньгах это накопительная ошибка. В Java — `BigDecimal`.
- **`TIMESTAMPTZ`, не `TIMESTAMP`.** Хранение в UTC, независимость от часовых поясов. В Java — `Instant`.
- **`GENERATED ALWAYS AS IDENTITY`**, не `BIGSERIAL` — стандарт SQL, в JPA соответствует `GenerationType.IDENTITY`.
- **`user_profiles` без собственного `id`.** PK совпадает с FK: профиль не может существовать без пользователя, и их не может быть два. Самый чистый способ сделать 1:1.
- **Индексы на внешние ключи созданы явно.** PostgreSQL, в отличие от MySQL, не индексирует FK автоматически. Без индекса запрос «курсы автора» и проверка при удалении идут полным сканом.
- **Индекса на `status` нет — намеренно.** Три возможных значения, селективность околонулевая. Индексы добавляются под замеренные проблемы, а не «на всякий случай».
- **Асимметрия каскадов.** Удаление пользователя уносит его записи и отзывы (`CASCADE`), но пользователя с курсами и курс с записанными студентами удалить нельзя (`RESTRICT`) — контент, за который заплатили, не должен исчезать. Вместо удаления — `ARCHIVED`.
- **Рейтинг курса не хранится в `courses`.** Считается через `AVG(rating)`. Кэшированное поле — денормализация, требующая синхронизации при каждом отзыве; вводится осознанно, если станет узким местом.
- **`CHECK` и `UNIQUE` дублируют валидацию в коде намеренно.** Код можно обойти (другой сервис, ручной SQL); ограничение в базе обойти нельзя. `UNIQUE(student_id, course_id)` — единственная надёжная защита от двойной записи при гонке параллельных запросов.

## 4. Бизнес-логика

### 4.1 Регистрация и аутентификация
- Email уникален; пароль хранится только как bcrypt-хеш.
- Логин возвращает JWT (access + refresh). Сессий на сервере нет — API stateless.
- Профиль создаётся вместе с пользователем в одной транзакции.

### 4.2 Курсы
- Создавать курсы может `INSTRUCTOR` и `ADMIN`. Автор фиксируется из токена, а не из тела запроса.
- Редактировать и удалять курс может только его автор (или `ADMIN`) — проверка **владения ресурсом**, не только роли.
- Публикация (`DRAFT → PUBLISHED`) — отдельная операция с предусловиями: заполнены название и описание, есть хотя бы один модуль и один урок.
- `DRAFT` виден только автору и админу. В публичном каталоге — только `PUBLISHED`.
- Удаление курса с активными записями запрещено — только перевод в `ARCHIVED`.

### 4.3 Записи на курс (Enrollment)
- Записаться можно только на `PUBLISHED` курс.
- Повторная запись на тот же курс запрещена (проверка в сервисе + `UNIQUE` в БД).
- Автор не может записаться на собственный курс.
- Прогресс — 0..100. Достижение 100 автоматически переводит статус в `COMPLETED`.
- Отмена записи (`CANCELLED`) не удаляет строку — история сохраняется.

### 4.4 Отзывы (Review)
- Оставить отзыв может только студент с записью на этот курс.
- Один отзыв на курс от одного пользователя; редактировать можно свой, удалять — свой или любой для `ADMIN`.
- Рейтинг 1..5. Средний рейтинг курса пересчитывается запросом при выдаче.

### 4.5 Каталог
- Пагинация обязательна, `findAll()` без ограничения не используется нигде.
- Фильтры: категория, диапазон цены, минимальный рейтинг, поиск по названию.
- Сортировка: по дате, цене, рейтингу, популярности (число записей).
- Реализация — JPA Specification: фильтры комбинируются, а не порождают десяток методов репозитория.

### 4.6 Инварианты уровня кода
- Сущность никогда не покидает сервисный слой — наружу только DTO.
- `equals`/`hashCode` на сущностях не генерируются Lombok'ом (`@Data` на entity — источник ошибок с ленивыми связями и `hashCode` по всем полям). Реализуются вручную по бизнес-ключу или не реализуются вовсе.
- Двунаправленные связи синхронизируются хелпер-методами (`course.addModule(m)` выставляет обе стороны).
- Все `@ManyToOne` объявлены `fetch = LAZY` — по умолчанию они `EAGER`, что тянет лишние джойны в каждом запросе.

## 5. API

Базовый путь `/api/v1`. Формат — JSON. Аутентификация — `Authorization: Bearer <token>`.

### Аутентификация
| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| POST | `/auth/register` | все | регистрация |
| POST | `/auth/login` | все | получить пару токенов |
| POST | `/auth/refresh` | все | обновить access-токен |

### Пользователи
| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| GET | `/users/me` | авторизованный | свой профиль |
| PATCH | `/users/me` | авторизованный | изменить профиль |
| GET | `/users/{id}` | все | публичный профиль автора |

### Курсы
| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| GET | `/courses` | все | каталог: пагинация, фильтры, сортировка |
| GET | `/courses/{id}` | все | карточка курса со структурой |
| POST | `/courses` | INSTRUCTOR | создать (статус DRAFT) |
| PATCH | `/courses/{id}` | автор | изменить |
| POST | `/courses/{id}/publish` | автор | опубликовать |
| POST | `/courses/{id}/archive` | автор | архивировать |
| DELETE | `/courses/{id}` | автор | удалить (только без записей) |
| GET | `/courses/my` | INSTRUCTOR | свои курсы, включая черновики |

### Модули и уроки
| Метод | Путь | Доступ |
|---|---|---|
| POST | `/courses/{courseId}/modules` | автор |
| PATCH / DELETE | `/modules/{id}` | автор |
| POST | `/modules/{moduleId}/lessons` | автор |
| GET | `/lessons/{id}` | записанный студент или автор |
| PATCH / DELETE | `/lessons/{id}` | автор |

### Записи
| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| POST | `/courses/{id}/enroll` | STUDENT | записаться |
| GET | `/enrollments/my` | STUDENT | мои курсы |
| PATCH | `/enrollments/{id}/progress` | владелец записи | обновить прогресс |
| POST | `/enrollments/{id}/cancel` | владелец записи | отменить |
| GET | `/courses/{id}/students` | автор курса | записанные студенты |

### Отзывы
| Метод | Путь | Доступ |
|---|---|---|
| GET | `/courses/{id}/reviews` | все |
| POST | `/courses/{id}/reviews` | записанный студент |
| PATCH / DELETE | `/reviews/{id}` | автор отзыва или ADMIN |

### Категории
| Метод | Путь | Доступ |
|---|---|---|
| GET | `/categories` | все |
| POST / PATCH / DELETE | `/categories[/{id}]` | ADMIN |

### Формат ошибок
Единый для всего API, через `@RestControllerAdvice`:

```json
{
  "timestamp": "2026-08-11T10:15:30Z",
  "status": 409,
  "error": "ALREADY_ENROLLED",
  "message": "Вы уже записаны на этот курс",
  "path": "/api/v1/courses/42/enroll"
}
```

Коды: `400` — валидация, `401` — нет/невалиден токен, `403` — нет прав на ресурс, `404` — не найдено, `409` — конфликт бизнес-правила.

## 6. Архитектура

```
com.the0shail.course_api
├── config        SecurityConfig, OpenApiConfig, JwtFilter
├── controller    REST-слой: DTO на входе, DTO на выходе, никакой логики
├── dto           request/response объекты (Java records)
├── entity        JPA-сущности, наружу не выходят
├── exception     свои исключения + GlobalExceptionHandler
├── mapper        MapStruct-интерфейсы
├── repository    интерфейсы Spring Data + Specification
├── security      UserDetails, JwtService, проверки владения
└── service       бизнес-логика, границы транзакций
```

Поток: `Controller → Service → Repository → БД`. Транзакции открываются в сервисном слое, не в контроллере и не в репозитории.

Альтернатива — укладка по фичам (`course/`, `enrollment/`), лучше масштабируется на больших кодовых базах. Выбор в пользу слоёв сделан осознанно из-за размера проекта.

### Ключевые настройки
```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate    # схемой владеет Flyway; расхождение = отказ старта
    open-in-view: false     # сессия Hibernate не живёт весь HTTP-запрос
```

`open-in-view: false` — принципиально. С включённым OSIV ленивые связи догружаются во время сериализации ответа, что маскирует `LazyInitializationException` и разносит N+1 по слоям. С выключенным всё необходимое грузится явно в сервисе.

## 7. Производительность

- **N+1 решается явно.** Списки со связями грузятся через `JOIN FETCH` или `@EntityGraph`. Контроль — по логу `org.hibernate.SQL`: один запрос вместо N+1.
- **Пагинация с fetch join** требует аккуратности: Hibernate не умеет пагинировать в БД при join fetch коллекции и делает это в памяти. Решение — двухшаговая загрузка (сначала страница id, потом данные) или `@BatchSize`.
- **DTO-проекции** для списков: каталог не тянет полные сущности с описаниями и содержимым уроков.
- **Индексы** под реальные запросы каталога, добавляются по результатам `EXPLAIN ANALYZE`.

## 8. Тестирование

**Юнит-тесты (JUnit 5 + Mockito):** сервисный слой с замоканными репозиториями. Покрываются бизнес-правила — повторная запись, публикация без уроков, отзыв без записи, прогресс вне диапазона.

**Интеграционные (Testcontainers + PostgreSQL):** репозитории и Specification против настоящей базы, применение миграций Flyway, срабатывание `UNIQUE` и `CHECK`, каскады при удалении.

**Слайс-тесты веб-слоя (`@WebMvcTest`):** маршрутизация, валидация, коды ошибок, правила доступа. В Boot 4 — `@MockitoBean` вместо удалённого `@MockBean`, MockMvc требует `@AutoConfigureMockMvc`.

Цель — покрытие бизнес-логики, а не процент строк.

## 10. Что этот проект демонстрирует работодателю

- Проектирование схемы БД: нормализация, ограничения целостности, осознанные каскады, индексы под запросы.
- Владение JPA за пределами туториалов: когда `@ManyToMany` неприменима, LAZY против EAGER, OSIV, диагностика и решение N+1.
- Миграции как единственный источник правды о схеме.
- Слоистая архитектура с чёткими границами и изоляцией сущностей от внешнего мира.
- Безопасность: stateless JWT, ролевая модель и — отдельно — проверка владения ресурсом.
- Тестирование на реальной СУБД вместо H2.
- Документированное API и предсказуемая обработка ошибок.

## 11. Возможные расширения

Не входят в основной объём, но обозначают направление развития:

- Кэширование каталога и рейтингов (Redis, `@Cacheable`).
- Загрузка материалов уроков в объектное хранилище (S3/MinIO).
- Асинхронные уведомления о публикации курса.
- Полнотекстовый поиск по каталогу (PostgreSQL FTS или Elasticsearch).
- Денормализованное поле рейтинга с пересчётом по событию — если `AVG` станет узким местом.
- CI на GitHub Actions: сборка, тесты, публикация образа.
